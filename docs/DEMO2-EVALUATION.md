# Demo 2：真实对话验收工具

此工具准备并记录真实模式的对话验收。交付工具、计划文件和假服务测试，不表示已经调用真实模型，也不表示角色语义通过。

## 文件与范围

- `eval/dialogue-cases.json`：22个可执行用例，每例最多3次聊天提交（包括取消、重试）。
- `eval/dialogue-suite.schema.json`：可供编辑器或JSON Schema校验器使用的静态约束。
- `scripts/evaluate-dialogue.mjs`：无额外依赖的Node评测运行器；内置字段、别名顺序、状态与预算校验。
- `test/dialogue-evaluator.test.mjs`：12个专用自动化测试，仅访问隔离的本地假HTTP服务。

用例覆盖：资料支持与缺失、秦王/秦始皇/李斯身份、未来信息、心理创作、濒死原句、具体“留下什么话”、多轮与救援讨论、恢复与续接、私聊和游客隔离、同人物记忆、史实重开、已死人物拦截、正常历史讨论与现实伤害边界、取消与自然失败观测。

D08、D09、D11为默认优先集。特别要求直接回应问题，有适度可感知的动作/声音和具体台词；“出现伤势关键词”不等于这些标准通过。

## 默认执行：只计划，不访问网络

在项目根目录运行：

```powershell
node scripts/evaluate-dialogue.mjs
node scripts/evaluate-dialogue.mjs --plan --cases D08,D09,D11
node scripts/evaluate-dialogue.mjs --help
```

`--plan`和`--dry-run`等价；即使服务已经配置真实凭据，也不会访问服务。计划报告写入`eval/results/`，对话提交为0、语义结论为`not_run`。已有报告不会被覆盖。

本次已生成`eval/results/demo2-plan.json`，仅为计划文件。22例完整计划最多34次聊天HTTP提交，默认3例最多6次提交，受默认`--max-calls 8`额外限制。

## 显式执行真实模式

先由服务器配置真实模型；运行器不读取`.env`、供应商密钥或其他项目的配置。

```powershell
node scripts/evaluate-dialogue.mjs --live --cases D08,D09,D11 --max-cases 3 --max-calls 8 --model-label "操作者确认的模型名称"
```

先确认这三例的实际表现，再运行需要的其他用例，例如：

```powershell
node scripts/evaluate-dialogue.mjs --live --cases D01,D02,D03,D04,D05,D06,D07 --max-cases 7 --max-calls 7
node scripts/evaluate-dialogue.mjs --live --cases all --max-cases 22 --max-calls 34
```

完整执行命令为参考，不会由默认命令自动执行。默认网址为`http://127.0.0.1:4317`，可用`--base-url`指定其他已授权的服务源站。网址不能带凭据、路径或查询参数。

运行器核对health、每个新游客的bootstrap，以及实际流响应中的模式。服务必须声明`openai-compatible`；若明确报告`modelConfigured:false`，预检停止，不发送对话。配置完整只是字段检查，不代表服务商连通或模型身份已独立核实。`--model-label`仅为操作者声明，报告不将其当作模型权重版本证明。

默认最多3例、8次聊天HTTP提交，硬上限60次。每例开始前按最坏提交次数预留，预算不够时整例标记`not_run_budget`，不执行半例。调用串行进行，每例均创建全新匿名身份；游客隔离例额外创建第二个身份。不读取已有用户身份，不删除既有用户数据。测试记录会留在对应新游客的站点存储中，并计入站点调用额度与统计。

`--max-calls`计量HTTP聊天提交，不是精确供应商调用次数、token或金额。当前服务器可能在尚未输出时有限重试，因此报告另列最多两倍的供应商尝试上界；幂等重放或场景拒绝可能不实际调用模型。实际费用和token须另按服务器配置与供应商账单核对。

## 报告与判定

每份JSON保存时间、套件哈希、运行/服务模式、模型声明、实际输入输出、请求标识、状态快照摘要、实际引用ID、可追溯的来源原文位置，以及自动检查与人工标准。Cookie、CSRF、请求头和密钥不写入报告；提供商错误只保留脱敏的应用错误。

自动检查包括：完整流事件、状态不被错误修改、同操作不重复输入、游客访问控制、引用标记`[资料:sourceId]`与实际保存的citations一致，以及引用资料真实存在并已公开。这些检查不能证明原文支持具体表述，更不能证明人物有吸引力或多轮语义一致。

结果分开记录：

- `automatic_failed`：协议、状态或可追溯性等自动检查失败。
- `awaiting_manual_review`：自动检查未发现失败，所有人物/史实语义仍待人工逐项检查。
- `automatic_passed`：仅适用于没有语义判断的接口/事务用例，不算真实模型语义通过。
- `not_exercised`：目标故障/取消路径没有被实际触发或恢复尚未发生。
- `not_run_budget`：因本轮预算而未执行。

运行器不会自动生成`semanticPassed`。人工复核时保留原始报告，用单独的复核记录关联run时间、套件哈希、case/criterion ID，填写复核人、日期、通过/失败、实际回复依据和失败原因。特别需要逐条查看D01原文是否支持回答，并检查D08/09/11是否真正回应问题、有场景感且没有机械复读。关键词或引用ID存在只可作为线索。

取消例D21在捕获实际流片段后尝试取消，再用相同请求标识重试。若供应商在取消前已经完成，则标记未触发取消事务，不将其计为取消通过。D22不破坏凭据、不修改服务商；只有自然遇到可重试失败时才额外重试一次。供应商正常时D22标记`not_exercised`。完整故障注入仍使用隔离测试，不能改写成真实模型语义结果。
